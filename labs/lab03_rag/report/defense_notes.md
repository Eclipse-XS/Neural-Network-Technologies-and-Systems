# Захист Lab 3: Варіант 3

Перші десять питань відповідають розділу «Контрольні запитання» наданої методички «ЛАБ 3.docx».

1. **У чому полягає основна ідея RAG?** Перед генерацією знайти релевантні зовнішні
   записи й додати їх до контексту LLM. Retrieval дає факти, generation формує відповідь.
2. **Чому LLM потребують зовнішніх джерел знань?** Параметрична пам’ять обмежена,
   може бути застарілою й не містить нашого CSV-каталогу. Контекст додає факти без перенавчання.
3. **Основні компоненти?** Джерело CSV, loader, row serialization/chunking, embedding model,
   vector index, retriever, prompt і LLM; окремо evaluation та provenance.
4. **Що таке семантичні embeddings і їхня роль?** Числові вектори змісту тексту.
   Одна модель відображає документи й питання в спільний простір для пошуку близьких записів.
5. **Векторний пошук проти ключових слів?** Ключові слова шукають лексичні збіги;
   embeddings можуть знайти перефразування. Семантична близькість не гарантує точні ID,
   числа й логічні умови, тому потрібні metadata та перевірки.
6. **Метрики подібності?** Cosine, dot product, Euclidean L2.
   cos(a,b)=(a·b)/(||a||·||b||). Redis COSINE distance=1−cos: нижче краще.
   Для одиничних векторів dot product дорівнює cosine similarity; метрика індексу явно COSINE.
7. **Як формується запит до LLM?** System визначає обмеження, контекст містить знайдені
   записи з джерелами й row ID, після нього питання. Дані не є інструкціями для моделі.
8. **Переваги проти чистої LLM?** Доступ до конкретного корпусу, оновлення фактів без
   навчання, можливість цитувати й перевіряти джерело. Це зменшує, але не усуває галюцинації.
9. **Прикладні задачі?** Пошук у документації, корпоративних знаннях, каталогах товарів,
   підтримка користувачів, аналіз наданих документів із посиланнями.
10. **Обмеження RAG?** Retrieval може пропустити джерело; корпус може містити помилки;
    контекст і embedding input обмежені. LLM може неправильно зіставити числа,
    ігнорувати відмову або виконати інструкції з даних. Додаються витрати індексації й підтримки.

## Конкретні рішення цієї роботи

- **Чому Redis є векторною БД?** Redis Stack Search індексує векторне поле HASH
  і виконує KNN-запити. LangChain RedisVectorStore використовує цей індекс.
- **Чому FLAT?** 185 записів — малий корпус. Точний перебір векторів простіший за
  приблизний HNSW. «Точний» означає пошук найближчих векторів, не правильність відповіді.
- **Що означає top-k=5?** Не більше п’яти найближчих записів у дозволеній filter-множині.
  Це компроміс контексту й coverage, не оптимальне k, знайдене tuning.
- **Навіщо row serialization?** Підписані поля пояснюють значення чисел і категорій.
  Один рядок залишається одиницею provenance; raw CSV не переписується.
- **Навіщо metadata?** source_file/row_id/product_id дають цитування й аудит;
  category — TAG filter; ціни й рейтинг — NUMERIC поля. У прикладі застосовано category filter.
- **Чому не SQL?** Семантичний KNN не обчислює MIN для всіх товарів. Навіть правильне
  порівняння retrieved records може пропустити глобально найдешевший товар.
- **Що показують метрики?** Hit@5 — чи є хоча б один еталонний ID; MRR — обернений
  ранг першого релевантного; Recall@5 — частка отриманих еталонних ID.
  Для q08 IR-метрики не обчислюємо, перевіряємо відмову вручну.
- **Чому grounding не гарантує істину?** Контекст може бути неповним чи суперечливим;
  правильна цитата може супроводжувати неправильний висновок. Лексичний збіг ціни цього не виявляє.
- **Чи всі 24 колонки embedded?** Ні. URLs і службові поля виключені, важливі поля
  та вибрані specifications серіалізовані. 17 довгих рядків обрізаються MiniLM; генерація отримує повний текст.
- **Як оброблено пропуски?** Missing discount лишається unknown; 0 rating із 0 count
  означає відсутність оцінок. Ціни й discount не виправляються на підставі припущень.
- **Чим корисний Redis для змішаного пошуку?** Вектори й структурні TAG/NUMERIC filters
  в одній системі. Недоліки — окремий сервіс, RAM, сумісність Search/клієнта та потреба в схемі.
- **Повторний запуск?** Кеш embeddings і fingerprint-index перевикористовуються;
  стабільні ключі не дублюються. Зміна даних породжує інший індекс, не видаляє старий.
- **Чи LLM завантажений Python?** Ні. LM Studio тримає модель; Python надсилає HTTP chat requests.
