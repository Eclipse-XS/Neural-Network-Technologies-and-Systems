# Лабораторна робота №2. Інтеграція LLM через API та open-source фреймворки

## Варіант 1 — LM Studio

## 1. Мета роботи

Мета роботи — інтегрувати локальну instruction-модель із Python-програмою через OpenAI-compatible API LM Studio. Реалізований CLI передає системну інструкцію, історію діалогу, `temperature` і `max_tokens`, отримує відповідь моделі та зберігає успішні діалоги для звіту. Окремі запуски з контрольованою зміною параметрів дають змогу якісно порівняти характер генерації.

## 2. Використане середовище

- LM Studio з увімкненим Local Model API;
- локальна адреса API: `http://localhost:1234/v1`;
- модель у LM Studio: Ministral 3 3B, API model id `mistralai/ministral-3-3b`;
- формат моделі: GGUF, квантування Q4_K_M;
- Python 3.11 або новіший;
- офіційний Python SDK `openai`, налаштований на локальний `base_url`.

Назва «Ministral 3 3B» відтворює позначення моделі в LM Studio. Вона не використовується тут як твердження про точну кількість усіх параметрів архітектури.

## 3. Архітектура

```text
User
  ↓
Python CLI
  ↓
OpenAI Python SDK
  ↓
POST /v1/chat/completions
  ↓
LM Studio local API
  ↓
Ministral 3 3B
  ↓
Assistant response
```

LM Studio UI керує локальною моделлю і сервером. Local Model API приймає HTTP-запити. Пакет `openai` у цій роботі є лише клієнтською бібліотекою для сумісного локального API. Генерація виконується моделлю в LM Studio, а не хмарним сервісом OpenAI. Значення `api_key="lm-studio"` є локальним placeholder, потрібним інтерфейсу SDK.

Перед початком діалогу програма викликає `/v1/models` через SDK і перевіряє точний model id. Модель не замінюється автоматично першою доступною моделлю.

## 5. Встановлення залежностей

Команди PowerShell із кореня репозиторію:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r labs/lab02_llm_api/requirements.txt
```

Якщо `.venv` уже існує, першу команду виконувати не потрібно.

## 6. Підготовка LM Studio

У LM Studio модель має бути доступна або завантажена, а Local Model API — мати статус `Running`. Для поточної конфігурації сервер працює за адресою `http://localhost:1234/v1`.

Перевірка з PowerShell:

```powershell
curl.exe http://localhost:1234/v1/models
```

Endpoint `/v1/models` підтверджує доступність сервера і показує model ids. Для типового запуску у відповіді має бути `mistralai/ministral-3-3b`.

## 7. Запуск CLI

Запуск із параметрами за замовчуванням:

```powershell
.\.venv\Scripts\python.exe -m labs.lab02_llm_api.src.cli
```

Власні параметри генерації:

```powershell
.\.venv\Scripts\python.exe -m labs.lab02_llm_api.src.cli `
    --system-prompt "You are a concise machine learning tutor." `
    --temperature 0.2 `
    --max-tokens 200
```

Інша локальна модель або адреса сервера задаються через `--model` і `--base-url`:

```powershell
.\.venv\Scripts\python.exe -m labs.lab02_llm_api.src.cli --model "another/model-id"
```

Команда `exit` завершує діалог. `quit`, `Ctrl+C` і кінець вводу також завершують сесію коректно. Після хоча б одного успішного обміну transcript записується в `outputs/dialogs/`.

## 8. Формування API request

Історія має структуру:

```text
system → user → assistant → user → assistant → ...
```

`system` задає загальну поведінку моделі. `user` містить поточне питання, а попередні `assistant`-повідомлення зберігають контекст. На кожному кроці до `client.chat.completions.create` передається повна поточна історія разом із новим питанням.

`temperature` керує варіативністю вибірки: нижче значення зазвичай робить відповідь передбачуванішою, вище — різноманітнішою. Окремий запуск не гарантує однаковості навіть за низького значення. `max_tokens` обмежує кількість токенів нової відповіді; він не обрізає історію діалогу.

## 9. Експерименти

Для коректного якісного порівняння за один раз змінюється одна змінна.

| Експеримент | System prompt | User prompt | Temperature | Max tokens | Мета |
|---|---|---|---:|---:|---|
| A | однаковий | однаковий | 0.2 | 200 | приклад низької варіативності |
| B | як в A | як в A | 1.2 | 200 | порівняння впливу temperature |
| C1/C2 | змінений між запусками | однаковий | 0.7 | 200 | порівняння системної інструкції |
| D | фіксований | питання і залежне follow-up | 0.7 | 200 | перевірка історії діалогу |

Один стохастичний приклад може продемонструвати відмінність, але не доводить статистично стійкого ефекту. Для строгого висновку потрібні повторні запуски та формальна метрика.

## 10. Результати

Unit tests перевіряють валідацію, видимість моделі, параметри API request, обробку порожньої відповіді, передавання історії та запис UTF-8 transcript без доступу до LM Studio. Контрольний запуск дав результат `15 passed`.

Local Model API повернув точний model id `mistralai/ministral-3-3b`. Через CLI виконано шість live-сесій, збережених в `outputs/dialogs/`; одна high-temperature сесія була повторною перевіркою, а остання — фінальним smoke test:

- `dialog_20261001_200119_010907.md` — temperature 0.2, system prompt інженера;
- `dialog_20261001_200131_879793.md` — temperature 1.2, перший high-temperature запуск;
- `dialog_20261001_200149_438685.md` — той самий запит і system prompt, temperature 1.2;
- `dialog_20261001_200211_040247.md` — temperature 0.7, system prompt для студента першого курсу;
- `dialog_20261001_200230_422568.md` — два пов'язані питання в одній сесії.
- `dialog_20261001_202953_833346.md` — фінальний smoke test із temperature 0.7 і max tokens 200.

У low- і high-temperature запусках модель сформулювала різні пояснення для однакового питання, але одного прикладу недостатньо, щоб віднести всю різницю лише до `temperature`. Зміна system prompt дала відповідь з додатковим вступним поясненням ролей validation і test. У multi-turn сесії другий request успішно отримав попередні `user` та `assistant` повідомлення; відповідь стосувалася вибору validation-процедури для виявлення overfitting.

За `max_tokens=100` кілька відповідей завершилися посеред речення. Це фактичне підтвердження того, що параметр обмежує нову відповідь. Для повніших прикладів у звіті доцільно використати 200–256 токенів, не змінюючи інші параметри експерименту.

## 11. Обробка помилок

- якщо сервер не запущено, CLI пояснює, як перевірити статус Local Model API;
- якщо model id відсутній у `/v1/models`, CLI показує потрібний і доступні ids;
- `temperature` перевіряється в діапазоні від 0 до 2;
- `max_tokens` має бути додатним цілим числом;
- порожній model id і порожній assistant content спричиняють явну помилку;
- питання додається до постійної історії лише після успішної відповіді.

## 12. Локальне та хмарне використання LLM

| Ознака | Локальна модель | Хмарна модель |
|---|---|---|
| Дані | обробляються в локальному середовищі | передаються зовнішньому сервісу згідно з його конфігурацією |
| Мережа | не потрібна для inference після локального налаштування | потрібна для API-запитів |
| Ресурси | обмежені локальним CPU, GPU і пам'яттю | інфраструктуру надає провайдер |
| Масштабування | потребує власного обладнання і налаштування | зазвичай простіше, але залежить від тарифів і лімітів |
| Вартість запиту | немає cloud request fee | можлива оплата за використання |

Хмарний API для цього варіанта не реалізується.

## 14. Короткі тези для захисту

- LLM — мовна нейронна модель, яка оцінює ймовірності токенів і генерує послідовність з урахуванням контексту.
- LM Studio завантажує та запускає сумісні моделі локально і може надавати до них HTTP API.
- OpenAI-compatible API дає змогу використати поширений формат запитів і готовий SDK без звернення до OpenAI cloud.
- `localhost:1234` означає порт 1234 на цьому комп'ютері; `/v1` є базовим шляхом API.
- System prompt задає інструкції щодо ролі, стилю або формату відповіді.
- `temperature` впливає на розподіл вибору наступного токена, але не гарантує конкретний результат.
- `max_tokens` є верхньою межею довжини нової відповіді.
- Локальний inference дає контроль над даними, але обмежений локальним обладнанням; хмарний спрощує доступ до потужніших ресурсів, але потребує мережі та може мати ціну використання.
- Модель працює без OpenAI cloud, тому що ваги та inference engine знаходяться в LM Studio.
- CLI повторно надсилає повну історію ролей, тому наступне питання може залежати від попередніх відповідей.

## 15. Висновки

Реалізовано інтеграцію локальної LLM через OpenAI-compatible API LM Studio. Python CLI є окремим клієнтом, перевіряє доступність точної моделі, передає системну інструкцію та історію, керує параметрами генерації й зберігає фактичні діалоги. Локальна схема не потребує хмарного inference. Вплив `system prompt` і `temperature` потрібно оцінювати за контрольованими live-запусками, не за вигаданими або mock-відповідями.
