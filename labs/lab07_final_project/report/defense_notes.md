# Відповіді на контрольні запитання

## 1. Які основні можливості забезпечують LLM та мультимоделі?

LLM генерують і перетворюють текст, узагальнюють, відповідають на питання та формують структуровані запити функцій. Мультимоделі поєднують текст із зображеннями чи іншими модальностями: наприклад, відповідають на питання про зображення. Конкретні можливості залежать від архітектури: використана у Lab 5 LLaVA не генерує зображення. Доступу до локальних документів LLM автоматично не має; його забезпечує застосунок.

## 2. Які два попередні компоненти інтегровано і яка їхня роль?

Із Lab 3 інтегровано LangChain + MiniLM + Redis RAG: зовнішні звіти перетворюються на індекс фрагментів, у якому знаходяться докази. Із Lab 6 — OpenAI Agents SDK, function tools та SQLiteSession: модель обирає функції, Runner виконує їх, а сесія зберігає контекст діалогу. LM Studio забезпечує локальний Chat Completions endpoint. Lab 7 має власний код і копії звітів, а не імпортує модулі цих лабораторних.

## 3. Що таке RAG і як він збагачує відповіді?

Retrieval-Augmented Generation додає до запиту фрагменти зовнішніх джерел. Тут питання кодує MiniLM, Redis знаходить найближчі вектори, а search_knowledge передає текст і ID агенту. Цей самий агент формує фінальну відповідь. Параметри LLM не змінюються, окремого генератора переказу немає. Цитата дозволяє перевірити твердження, але ні близький вектор, ні справжній ID не гарантують правильного висновку.

## 4. Які практичні сценарії демонструє проєкт?

Пошук моделі в приватному звіті, порівняння двох лабораторних, знаходження кількостей із подальшою арифметикою, уточнення попереднього питання через пам’ять та відмова назвати невідому температуру. Експерименти перевіряють можливості та невдачі: числовий сценарій не завершив потрібну арифметику, хоча детермінований калькулятор пройшов preflight.

## 5. Які переваги надає інтеграція декількох інструментів?

RAG дає доступ до приватних знань, функції — перевірювані дії, пам’ять — зв’язок між ходами. У контрольній парі про невідому температуру plain LLM вигадала +18°C, а асистент відмовився визначати число. Інтеграція додає latency, залежність від Redis та помилки вибору й синтезу. Вона не гарантує перевагу в кожному запиті: у багатокроковому сценарії правильного результату не було в обох варіантів.

## Короткі уточнення для захисту

- **Чому FLAT?** 121 вектор; exact search достатній, HNSW не потрібний.
- **Що означає distance?** COSINE distance, менше — ближче; не відсоток впевненості.
- **Чому CPU embeddings?** Невеликий encoder, GPU потрібний локальній LLM.
- **Пам’ять і RAG?** SQLite містить діалог; Redis — зовнішні звіти.
- **Де рішення агента?** У реальних function calls, а не у заявленому текстовому плані.
- **Чому не 100%?** 76 фрагментів перевищують ліміт encoder, пошук може пропустити факт, модель може неправильно використати навіть правильний фрагмент.
- **Що поліпшувати наступним експериментом?** Поділ за токенами, мультимовні embeddings, оцінювання саме answer-bearing chunks, а не лише source hit. Це рекомендації, не виконані порівняння.
