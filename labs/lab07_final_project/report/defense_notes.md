# Конспект для захисту фінального проєкту (Лабораторна робота №7)

**Тема:** Автономний локальний асистент інженерних знань (Local Engineering Knowledge Copilot)

---

## 1. Контрольні запитання та академічні відповіді

### 1.1. Які основні можливості забезпечують LLM та мультимодальні моделі?
- **Великі мовні моделі (LLM)**: забезпечують розуміння природної мови, генерацію відповідей, синтез фактів, форматування коду та виклик структурованих функцій (Function Calling / Tool Calling). За замовчуванням локальна LLM не має доступу до приватних файлів і схильна до галюцинацій та арифметичних помилок.
- **Мультимодальні моделі (VLM, як-от LLaVA у Lab 5)**: додатково поєднують зорові енкодери (CLIP, SigLIP) з мовною моделлю, дозволяючи відповідати на запитання щодо візуальних артефактів.
- **Роль Copilot**: інтеграційна система ізолює мовну модель від прямого доступу до середовища, транслює запити користувача у верифіковані виклики пошуку (`search_knowledge`) та обчислень (`calculate`), заземлюючи відповіді на перевірені факти.

### 1.2. Які компоненти попередніх лабораторних робіт було інтегровано?
1. **З Lab 3 (RAG)**: концепцію семантичного векторного індексу та векторизації текстів. У фінальній архітектурі її суттєво вдосконалено переходом на `intfloat/multilingual-e5-small` (384-d вектори з асиметричним префіксуванням `query:` / `passage:`), повнотекстовий лексичний індекс `BM25Okapi` та злиття рангів `Reciprocal Rank Fusion (RRF)`.
2. **З Lab 6 (Agents)**: парадигму агентного циклу (ReAct), виклик детермінованих інструментів та сесійну персистентність діалогу в SQLite (режим WAL).

### 1.3. Що таке RAG і як він збагачує генерацію?
RAG (Retrieval-Augmented Generation) — це патерн, за якого перед генерацією відповіді система вилучає найбільш релевантні фрагменти (докази) з зовнішнього корпусу знань і передає їх у контекст мовної моделі. Це дозволяє:
- оперувати актуальними або конфіденційними даними без донавчання моделі;
- надавати точні посилання на джерела у форматі `[document_id#chunk_id]`;
- звести до мінімуму фактологічні галюцинації.

### 1.4. Які практичні сценарії демонструє розроблена система?
1. **Точний пошук фактів (Exact Fact)**: знаходження гіперпараметрів, версій бібліотек та конфігурацій попередніх робіт (наприклад, планувальник PNDMScheduler у Lab 4, вага моделі LLaVA у Lab 5).
2. **Міждокументний синтез (Cross-Document Synthesis)**: зіставлення підходів та результатів між різними лабораторними роботами.
3. **Детерміновані чисельні розрахунки (Numerical Reasoning)**: виконання математичних операцій через AST-калькулятор без залучення авторегресійних чисельних здогадок LLM.
4. **Контрольована відмова (Abstention on Unsupported Queries)**: відмова від надання відповіді у разі відсутності фактів у локальній базі (100% успішність на 15 контролях).
5. **Багатокрокова пам’ять із сесійною ізоляцією**: ведення діалогу зі збереженням сутностей контексту без крос-сесійного витоку.

### 1.5. Які переваги та компроміси надає інтеграція мульти-інструментального контуру?
- **Переваги**:
  - надійність чисельних операцій (0% помилок калькулятора);
  - верифікованість тверджень через явні посилання на пасажі;
  - локальність та відсутність витоку даних назовні.
- **Компроміси (Trade-offs)**:
  - збільшення латентності через послідовні фази пошуку, перевірки та інференсу;
  - вимога до локальних ресурсів (щонайменше 8-16 ГБ RAM для комфортної роботи Redis + LLM);
  - складність налаштування ваг злиття рангів RRF для запобігання міждокументному витісненню.

## 2. Швидкі технічні тези для захисту

- **Чому Redis Stack?** Висока швидкість (пошук < 10 мс), підтримка як плоского індексу FLAT (для малих корпусів), так і HNSW (для великих), гнучке збереження метаданих.
- **Чому `multilingual-e5-small`?** Підтримка української мови, компактний розмір (384-d, 133 млн параметрів), висока швидкість інференсу на звичайному CPU, відкрита ліцензія.
- **Як вирішено проблему Silent Truncation?** Застосовано ієрархічне розбиття за заголовками Markdown із контролем бюджету токенів (window=400 токенів, overlap=60 токенів) та детермінованим хешуванням SHA-256. Результат: **0 Truncation Violations**.
- **Чому AST замість `eval()`?** Функція `eval()` створює пряму загрозу Remote Code Execution (RCE). AST-аналізатор на рівні компілятора Python дозволяє лише базові математичні оператори над константами, унеможливлюючи виклики системних функцій чи ін’єкції.
- **Які фактичні результати бенчмарку?**
  - Оцінено: 100 запитів (85 підтримуваних, 15 контрольних).
  - Гібридний пошук: Recall@1 = 0.5721, Recall@5 = 0.9029, Hit@5 = 0.9647, MRR = 0.8363.
  - Чисельні запити: Hit@5 = 1.0000, Recall@5 = 1.0000.
  - Контрольована відмова: 100% (15 із 15).
  - Всі 185 автоматизованих тестів бекенду пройшли успішно.
- **Чому не досягнуто цільових 0.75 за Recall@1?** Через відсутність другого етапу переранжування (Cross-Encoder reranking) та явище взаємного витіснення пасажів при міждокументному пошуку. Це чесний науковий результат, відображений у звіті.
